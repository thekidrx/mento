# Photo Memories — Design

## Purpose

Give the two users of R&S Web a shared place to keep photos of their
time together, browsable by date, on the same private site as their
calendar and notes.

Success looks like: either person can add photos from their phone in
under a minute, both can scroll back through them by month, and the
photos are visible to nobody who is not logged in.

## Decisions made with the user

- **One timeline by date.** No albums. Photos are shown newest first,
  grouped by month.
- **Optimised copies, not originals.** Each photo is shrunk before it
  is saved. The site is not a replacement for a camera roll.
- **Shrinking happens in the browser before upload.** The server
  stores what it is sent and adds no image-processing dependency.
- **Only the uploader can edit or delete a photo** (same rule as
  notes). Both users can view everything.
- **Photos live in the existing `data` folder on the Pi** and are
  included in the nightly backup, which never deletes from its copy.

## What the user sees

A new **Photos** tab sits between Lists and Wordle, with its own icon.

**Timeline**
- Page heading "Photos" with a short subtitle and an "Add photos"
  button.
- Month headings ("November 2026"), newest month first. Under each, a
  grid of square thumbnails, newest first: three columns on a phone,
  more on wider screens.
- Thumbnails load lazily as they scroll into view.
- Empty state: the cat mascot with "No photos yet".

**Adding photos**
- "Add photos" opens the device's photo picker; several photos can be
  chosen at once, up to 20 per batch. Choosing more than 20 keeps the
  first 20 and says so.
- Chosen photos appear in a staging panel above the timeline. Each
  row shows a small preview, a date field, an optional caption field
  (up to 200 characters) and a remove button.
- The date is pre-filled from the file's last-modified date, capped at
  today. It can be changed. Future dates are not accepted.
- "Upload 3 photos" uploads them one at a time and shows progress
  ("Uploading 2 of 3"). Each photo that succeeds leaves the staging
  panel and appears in the timeline. A photo that fails stays in the
  panel with its error, so it can be retried or removed.
- A file the browser cannot read as an image (for example an
  unsupported format) is rejected when chosen, with "Couldn't read
  <filename>".
- "Cancel" clears the staging panel. Nothing is saved until Upload is
  pressed.

**Viewing a photo**
- Tapping a thumbnail opens a full-screen viewer over the page: the
  photo scaled to fit, its caption, its date ("Saturday, November 14,
  2026") and "Added by Ryan".
- Previous and next buttons move through the timeline in the order
  shown. Left and right arrow keys do the same; Escape closes.
- A close button is always visible. Focus moves into the viewer when
  it opens and returns to the thumbnail when it closes.
- For a photo the current user uploaded, the viewer also shows Edit
  (change date and caption) and Delete. Delete asks for confirmation
  in the viewer before doing anything, then shows the next photo, or
  closes if none remain.

Styling follows the existing design tokens, cards, buttons and fields.
The page must not scroll horizontally at 375px width, and the six tabs
must fit both the top bar (checked at 768px and 1280px) and the phone
bottom bar (checked at 375px) without overlapping or clipping.

## Image handling in the browser

For each chosen file the client produces two JPEGs with a canvas:

| Output | Longest side | JPEG quality |
| --- | --- | --- |
| Photo | at most 2000px | 0.85 |
| Thumbnail | at most 480px | 0.75 |

- Images smaller than the limit are not enlarged.
- The image is decoded with the browser's normal image loading, which
  applies the camera's rotation, so photos are stored upright.
- Re-encoding through a canvas drops all embedded metadata, including
  GPS location. This is intended.
- Transparent areas (from a PNG) are filled white.

## Data model

One new table in `server/schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS photos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  file_key TEXT UNIQUE NOT NULL,
  taken_on TEXT NOT NULL,
  caption TEXT,
  created_by INTEGER NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- `taken_on` is a `YYYY-MM-DD` date.
- `file_key` is 32 random hex characters generated by the server. It
  never comes from the client.

Files on disk, in the photos directory:
- `<file_key>.jpg` — the photo
- `<file_key>.thumb.jpg` — the thumbnail

The photos directory is `PHOTOS_DIR` if set, otherwise a `photos`
folder beside the database file. With the existing Docker setup
(`DB_PATH=/data/app.db`, `./data:/data`) that is `data/photos` on the
Pi, with no change to `docker-compose.yml`. The directory is created
on startup if missing. `createApp(db, options)` takes it as
`options.photosDir` so tests can use a temporary folder.

## API

New router `server/routes/photos.js`, mounted at `/api/photos` behind
`requireAuth`.

| Method and path | Body | Result |
| --- | --- | --- |
| `GET /api/photos` | | All photos, `taken_on` descending then `id` descending, each with `display_name` of the uploader |
| `POST /api/photos` | `{ image, thumb, taken_on, caption }` | 201 with the new photo |
| `PUT /api/photos/:id` | `{ taken_on, caption }` | The updated photo |
| `DELETE /api/photos/:id` | | `{ ok: true }` |
| `GET /api/photos/:id/image` | | The photo, `Content-Type: image/jpeg` |
| `GET /api/photos/:id/thumb` | | The thumbnail, `Content-Type: image/jpeg` |

`image` and `thumb` are base64-encoded JPEG data with no `data:`
prefix. The photo JSON never includes `file_key`.

**Request size.** The app's JSON body limit stays at its default for
every other route. `/api/photos` gets its own JSON parser with an 8 MB
limit, applied after the session and auth check so a logged-out client
cannot make the server read a large body. This requires the session
middleware to move ahead of the JSON parser in `server/app.js`. A body
over the limit returns 413 with `{ error: 'Photo is too large' }`.

**Validation**, all as JSON `{ error }` with status 400 unless noted:
- `image` and `thumb` must be strings of valid base64 that decode to
  data starting with the JPEG signature bytes `FF D8 FF`. Otherwise
  "Photo must be a JPEG image".
- Decoded `image` over 5 MB or decoded `thumb` over 300 KB: 413
  "Photo is too large".
- `taken_on` must match `YYYY-MM-DD`, be a real calendar date, and not
  be later than tomorrow in UTC (one day of slack for time zones).
  Otherwise "A valid date is required".
- `caption` is optional. If present it must be a string; it is trimmed
  and an empty result is stored as null. Over 200 characters:
  "Caption must be 200 characters or fewer".
- Unknown or non-numeric id: 404 "Photo not found".
- `PUT` or `DELETE` by someone other than the uploader: 403 "You can
  only change photos you added".

**Files and the database stay consistent.**
- Upload writes both files first, then inserts the row. If the insert
  fails, both files are removed.
- Delete removes the row first, then both files. A file that is
  already missing is not an error.
- `GET .../image` or `.../thumb` for a row whose file is missing
  returns 404 "Photo not found".

**Serving.** Files are sent only through the two authenticated routes;
the photos directory is never exposed as a static folder. Responses
carry `Cache-Control: private, max-age=31536000, immutable`, since the
bytes for a given id never change, and
`X-Content-Type-Options: nosniff`.

## Client

- `client/src/api.js`: `getPhotos()`, `uploadPhoto({ image, thumb,
  taken_on, caption })`, `updatePhoto(id, { taken_on, caption })`,
  `deletePhoto(id)`, plus `photoUrl(id)` and `thumbUrl(id)` returning
  the two image paths.
- `client/src/pages/Photos.jsx`: `PhotosPage`, holding the photo list,
  the staging list and which photo is open.
- `client/src/components/PhotoUploader.jsx`: the staging panel and
  upload loop.
- `client/src/components/PhotoViewer.jsx`: the full-screen viewer with
  edit and delete.
- `client/src/pages/photosLogic.js`: pure helpers with unit tests.
  - `groupByMonth(photos)` returns `[{ key: '2026-11', label:
    'November 2026', photos: [...] }]`, preserving order.
  - `scaledSize(width, height, maxSide)` returns `{ width, height }`
    rounded to whole pixels, never enlarging.
  - `defaultTakenOn(lastModifiedMs, now)` returns a local `YYYY-MM-DD`
    date, capped at today.
  - `isUsableDate(dateKey, now)` is true for a real date not after
    today.
- `client/src/pages/imageResize.js`: `resizeToJpeg(file, maxSide,
  quality)` returning base64, using an `<img>` and a canvas. Browser
  only; verified by hand, not unit tested.
- `client/src/components/Icons.jsx`: `PhotoIcon`, `PlusIcon`,
  `CloseIcon`.
- `client/src/App.jsx`: the Photos tab, and passing `currentUserId`.
- `client/src/index.css`: grid, staging panel and viewer styles.

**Refresh behavior.** The timeline reloads after each successful
upload, edit or delete, and when the browser tab becomes visible again
(reusing `useRefreshOnVisible`), unless the staging panel has photos
in it or the viewer is open.

**Errors.** A failed load shows the error instead of the empty state.
Upload, edit and delete errors show inline next to the control that
caused them and leave the user's input in place. Upload and Delete
ignore repeat taps while a request is in flight.

## Backups

`scripts/backup.sh` gains one step after the database backup: copy
every file in `data/photos` that is not already in
`data/backups/photos` into it, without overwriting and without
deleting anything. A photo deleted on the site therefore remains in
the backup folder and can be recovered by hand. The step is skipped
cleanly if `data/photos` does not exist yet.

This backup is on the same Pi and the same card. It protects against
accidental deletion, not hardware failure. That limit already applies
to the database backup and is unchanged here.

## Testing

- `server/__tests__/photos.test.js`, using an in-memory database and
  a temporary photos directory that is removed after each test:
  - upload stores both files and returns the photo without
    `file_key`; list ordering; the two image routes return the exact
    bytes with the right headers;
  - the other user can view but gets 403 on edit and delete;
  - edit changes date and caption; delete removes the row and both
    files;
  - every validation case above, including bad base64, non-JPEG
    bytes, oversized image, oversized thumb, each kind of bad date,
    long caption and non-string caption;
  - unknown and non-numeric ids; a row whose file is missing;
  - a failed insert leaves no files behind;
  - all routes reject an unauthenticated request with 401, and an
    unauthenticated oversized upload gets 401, not 413;
  - other routes still reject a JSON body over the default limit.
- `client/src/__tests__/photosLogic.test.js` for the four helpers.
- Manual check in the browser at 375px, 768px and 1280px, as each
  account: upload several photos including a portrait phone photo and
  a PNG with transparency, confirm orientation, month grouping, the
  viewer's keyboard controls, edit, delete, the other account's
  restricted view, a failed upload staying staged, and that an image
  address returns 401 after logging out.
- `scripts/backup.sh` run twice against a scratch data folder: photos
  are copied once, a photo deleted from `data/photos` remains in the
  backup, and the script succeeds when `data/photos` is absent.

## Deployment

No new dependencies or required environment variables. On the Pi:
`git pull`, then `docker compose up -d --build app`. The table and the
`data/photos` folder are created on startup.

## Out of scope

- Albums, tags or search.
- Videos and live photos.
- Comments or reactions on photos.
- Downloading all photos as an archive.
- Swipe gestures in the viewer.
- A storage quota or disk-space warning.
- Keeping original files or embedded metadata.
- Reading the capture date from inside the file.
